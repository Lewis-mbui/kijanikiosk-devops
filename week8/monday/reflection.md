## Question 1: The Layer Caching Decision

During the rebuild test, I modified a single line in `src/payments.js` by adding a temporary comment and rebuilt the Docker image. Docker reused the cached layers for the `FROM node:18-alpine`, `WORKDIR /app`, `COPY package.json package-lock.json ./`, and `RUN npm ci --only=production` instructions because neither the base image nor the package manifest files had changed. The first cache miss occurred at the `COPY . .` instruction because it copies the application source files, including `src/payments.js`. Once this layer was invalidated, Docker rebuilt it and then recreated the remaining layers (`EXPOSE` and `CMD`) as part of the new image. The expensive dependency installation step was skipped because its inputs were unchanged, making the rebuild much faster.

The behaviour changes when `package.json` or `package-lock.json` is modified to add a new dependency. In that case, the `COPY package.json package-lock.json ./` layer becomes the first cache miss. Since the `RUN npm ci --only=production` layer depends on those files, Docker must reinstall the dependencies before continuing with the remaining layers. Even if no application source files have changed, every layer after the package manifest copy must be rebuilt because Docker can only reuse cached layers when all previous layers are identical. This instruction ordering keeps everyday source code changes fast while still ensuring that dependency changes produce a correct and reproducible image.

## Question 2: Containers and the Week 7 Deployment

In Week 7, the deployment process depended on the target virtual machine already being prepared in a very specific way. The deployment script downloaded a tarball from Nexus, extracted it into the expected directory structure under `/opt/kijanikiosk`, and restarted the systemd service. This only worked because the VM already had the correct version of Node.js installed, npm available, the required service accounts created, the application directories provisioned by Ansible, and the systemd unit files configured to start the application. If any of these prerequisites differed between servers, the deployment could fail even though the application artifact itself was correct.

The container approach removes these assumptions by packaging the application together with its runtime and dependencies into a Docker image. The `FROM node:18-alpine` instruction guarantees that every container starts from the same Node.js runtime regardless of the host operating system. The `WORKDIR` and `COPY` instructions create the required directory structure and place the application files in the correct location inside the image, eliminating the need for Ansible to prepare application directories. The `RUN npm ci --only=production` instruction installs the exact production dependencies during image creation, so the target machine does not need npm packages installed beforehand. Finally, the `docker run` command replaces the systemd service by creating and starting a container directly from the image. The host machine only requires Docker to be installed; the application runtime, filesystem layout, and dependencies are all supplied by the image itself, making deployments consistent across different servers.

## Question 3: CMD Exec Form vs Shell Form

The `CMD ["npm", "start"]` form is considered an anti-pattern because it introduces an extra process between Docker and the Node.js application. When a container starts with `npm start`, the container's main process becomes the npm process, which then launches the Node.js application as a child process. When `docker stop` is executed, Docker sends a `SIGTERM` signal to the container's main process, which is npm rather than Node.js. Since npm does not reliably forward this signal to its child process, the Node.js application may never receive the shutdown request. After Docker waits for its default timeout, it forcefully terminates the container with `SIGKILL`, preventing the application from performing a graceful shutdown.

Using the exec form, `CMD ["node", "dist/index.js"]`, makes the Node.js process the container's main process (PID 1). When Docker sends `SIGTERM`, the Node.js application receives it directly and can execute its shutdown logic before exiting. In my application, this allowed the server to close cleanly when I stopped the container, demonstrating the expected graceful shutdown behaviour.

For a payment service, graceful shutdown is important because it allows the application to finish processing in-flight requests, close network connections, and release resources before terminating. If the service is stopped abruptly with `SIGKILL`, requests that are being processed can be interrupted, potentially leaving operations incomplete or clients receiving failed responses. Using the exec form improves the reliability of service shutdowns and reduces the risk of disrupting active transactions.
