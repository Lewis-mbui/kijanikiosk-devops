# Comparing Blue/Green Deployment and Container-Based Deployment for KijaniKiosk Payments

Over the past two weeks we have implemented two different approaches for deploying the KijaniKiosk Payments service. The first approach used separate blue and green environments running on virtual machines. The second approach packages the application into a container and runs it on a Kubernetes cluster. Both approaches successfully deliver the application, but they solve operational problems in different ways and provide different levels of automation.

The blue/green approach focused on reducing deployment risk. Before changing customer traffic, a complete new environment was prepared and verified independently. Once testing was successful, traffic was switched to the new environment. If a problem was discovered, traffic could be switched back to the previous environment almost immediately because both versions were already running. This provided a predictable and low-risk deployment process while still requiring engineers to perform the traffic switch and rollback decisions.

The container-based approach focuses on maintaining the desired state of the application automatically. Instead of thinking about individual servers, the platform is instructed how many copies of the application should always be running. During this project, two application replicas were deployed, and the platform continuously monitored them. When one replica was deliberately deleted, the remaining replica continued serving requests while a replacement was created automatically. The measured recovery time during this exercise was **17 seconds**, demonstrating that application recovery no longer depends on an engineer noticing the failure before taking action.

Another significant improvement is application packaging. The earlier development-oriented container included unnecessary build tools that were only required while compiling the application. The production image removes those tools and contains only what is needed to run the service. This reduced the image from a **361 MB** single-stage build to a production image with **47.1 MB** of application content, making transfers faster while also reducing the amount of software included in production.

Although both approaches improve reliability, they do so in different ways. Blue/green deployment minimizes deployment risk by maintaining two complete environments and allowing rapid traffic switching between them. The container approach improves operational resilience by automatically recreating failed application instances and continuously maintaining the desired number of running replicas. Rather than relying on manual operational actions, the platform continuously monitors the running application and corrects failures automatically.

| Concern                  | Blue/Green Approach                                                                                                                         | Container-Based Approach                                                                                                                                                                  |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Deployment mechanism** | A complete second environment is deployed, validated, and then traffic is switched to the new version.                                      | A Deployment maintains the desired number of replicas and schedules Pods automatically across the cluster.                                                                                |
| **Rollback mechanism**   | Traffic is redirected back to the previously running environment, making rollback almost immediate because both versions already exist.     | Rolling updates replace Pods gradually. If a rollback is required, the Deployment is updated to the previous image version and Kubernetes reconciles the workload automatically.          |
| **Failure recovery**     | A failed service requires operational intervention such as restarting the application or switching traffic back to the healthy environment. | Failed Pods are recreated automatically. During this project one replica continued serving requests while a replacement Pod was created, with a measured recovery time of **17 seconds**. |
| **Scaling**              | Increasing capacity requires provisioning additional infrastructure and deploying additional application instances manually.                | Replica count is increased declaratively, allowing Kubernetes to create additional Pods automatically whenever sufficient cluster resources are available.                                |

The container-based solution represents a major improvement in operational automation, but it does not yet solve every production concern. External traffic management, advanced routing, secure public access, and controlled exposure of multiple services are still outside the scope of this project. The application is currently accessed through a development-oriented service that is suitable for testing but not for a production internet-facing platform. The next Kubernetes project builds on this foundation by introducing orchestration features that manage external traffic more effectively while continuing to provide the self-healing, scaling, and automated deployment capabilities demonstrated during this week's work.
